# SIEM/EDR Synthetic Data Generation Plan

## Overview

This plan describes the design for generating synthetic security data that mimics what a typical Security Information and Event Management (SIEM) or Endpoint Detection and Response (EDR) system would see across a network. The data is designed to be **correlated** across all entities - events from hosts directly drive logs in firewalls, IDS/IPS, DNS, VPN, proxies, and routers.

## Entity Design

### 1. Host Entity (Core)
The host entity is the **central entity** that drives all other log generation. Each host represents an endpoint in the network.

**Columns:**
- `host_id`: Unique identifier (HOST_001, HOST_002, ...)
- `hostname`: Human-readable name (ws-finance-001, srv-web-01)
- `ip_address`: IPv4 address (10.x.x.x private network)
- `mac_address`: MAC address
- `host_type`: workstation, server, laptop, mobile, iot_device
- `os_type`: Windows, Linux, macOS
- `department`: Finance, Engineering, HR, IT, Sales, Executive
- `risk_level`: low, medium, high (for user-based targeting)
- `is_privileged`: Whether this is an admin/privileged host

**Cardinality:** 200 hosts

### 2. User Entity
Users that operate on hosts and authenticate to systems.

**Columns:**
- `user_id`: Unique identifier (USER_001, ...)
- `username`: Login name (jsmith, admin01)
- `email`: Corporate email
- `department`: Finance, Engineering, HR, IT, Sales
- `role`: employee, contractor, admin, service_account
- `is_privileged`: admin rights flag
- `fk_primary_host_id`: Primary assigned workstation

**Cardinality:** 150 users

### 3. Network Session Entity (State Machine)
Models host network activities. This is the **bridge entity** that connects hosts to all network log types.

**State Machine States:**
- IDLE → DNS_LOOKUP → CONNECTION_INIT → ESTABLISHED → DATA_TRANSFER → CLOSE
- Alternative paths: DNS_LOOKUP → BLOCKED (firewall), ESTABLISHED → IDS_ALERT → RESET

**Columns:**
- `session_id`: Unique session identifier
- `fk_host_id`: Source host (foreign key)
- `fk_dest_host_id`: Destination host (for internal traffic, nullable)
- `dest_ip`: Destination IP (external or internal)
- `dest_port`: Destination port
- `protocol`: TCP, UDP, ICMP
- `application`: HTTP, HTTPS, SSH, RDP, SMB, DNS, etc.
- `bytes_sent`, `bytes_received`: Traffic volume
- `session_state`: Current state machine state
- `action_type`: Trigger that caused transition

**Cardinality:** 10,000 sessions

### 4. Firewall Log Entity
Logs generated by network sessions passing through the firewall.

**Columns:**
- `log_id`: Unique log identifier
- `fk_session_id`: Reference to network session
- `timestamp`: Event time
- `src_ip`, `dst_ip`, `src_port`, `dst_port`
- `protocol`: TCP, UDP, ICMP
- `action`: ALLOW, DENY, DROP, REJECT
- `rule_id`: Matched firewall rule
- `bytes`: Traffic size
- `zone_src`, `zone_dst`: trust, untrust, dmz, internal

**Correlation:** Generated from network_session entity - every session generates 1+ firewall log entries

**Cardinality:** Derived from sessions (~15,000 entries)

### 5. IDS/IPS Alert Entity
Intrusion detection alerts triggered by suspicious sessions.

**Columns:**
- `alert_id`: Unique alert identifier
- `fk_session_id`: Reference to triggering session
- `timestamp`: Detection time
- `signature_id`: IDS signature that matched
- `signature_name`: Human-readable signature name
- `severity`: critical, high, medium, low, info
- `category`: malware, exploit, policy_violation, recon, lateral_movement
- `action`: alert, block, drop
- `src_ip`, `dst_ip`

**Correlation:** Only sessions with certain characteristics generate IDS alerts (e.g., suspicious ports, known bad destinations)

**Cardinality:** ~500-1000 alerts (5-10% of sessions)

### 6. DNS Log Entity
DNS queries made by hosts during network sessions.

**Columns:**
- `query_id`: Unique query identifier
- `fk_session_id`: Reference to network session
- `fk_host_id`: Querying host
- `timestamp`: Query time
- `query_name`: Domain queried
- `query_type`: A, AAAA, MX, TXT, CNAME
- `response_code`: NOERROR, NXDOMAIN, SERVFAIL, REFUSED
- `response_ip`: Resolved IP address
- `ttl`: Time-to-live
- `is_suspicious`: Flag for DGA/suspicious domains

**Correlation:** Network sessions that involve DNS lookups generate DNS logs

**Cardinality:** ~8,000 queries

### 7. VPN Log Entity
VPN connection events for remote access.

**Columns:**
- `vpn_event_id`: Unique event identifier
- `fk_user_id`: Connecting user
- `timestamp`: Connection time
- `event_type`: connect, disconnect, auth_success, auth_failure
- `source_ip`: External IP address
- `assigned_ip`: Internal VPN IP assigned
- `tunnel_type`: SSL, IPSec, L2TP
- `duration_seconds`: Session duration
- `bytes_transferred`: Total traffic
- `geo_location`: Country/region of source IP

**Cardinality:** ~1,000 VPN events

### 8. Proxy Log Entity
Web proxy logs for outbound HTTP/HTTPS traffic.

**Columns:**
- `proxy_log_id`: Unique log identifier
- `fk_session_id`: Reference to network session
- `fk_host_id`: Source host
- `timestamp`: Request time
- `method`: GET, POST, PUT, DELETE, CONNECT
- `url`: Full URL requested
- `domain`: Extracted domain
- `user_agent`: Browser/client user agent
- `response_code`: HTTP status code
- `content_type`: MIME type
- `bytes_in`, `bytes_out`: Traffic volume
- `category`: business, social_media, streaming, malware, uncategorized
- `action`: allow, block, warn

**Correlation:** HTTP/HTTPS sessions generate proxy logs

**Cardinality:** ~6,000 proxy logs

### 9. Endpoint Log Entity (EDR)
Host-based events captured by endpoint agents.

**Columns:**
- `event_id`: Unique event identifier
- `fk_host_id`: Source host
- `fk_user_id`: Associated user (if applicable)
- `timestamp`: Event time
- `event_type`: process_start, process_stop, file_create, file_modify, file_delete, registry_modify, network_connect, dll_load
- `process_name`: Process executable name
- `process_path`: Full path to executable
- `process_hash`: SHA256 hash of executable
- `parent_process`: Parent process name
- `command_line`: Full command line (for process events)
- `file_path`: Target file path (for file events)
- `registry_key`: Registry key (for registry events)
- `severity`: info, low, medium, high, critical

**Cardinality:** ~20,000 endpoint events

### 10. Netflow Record Entity
Router-generated flow records summarizing traffic.

**Columns:**
- `flow_id`: Unique flow identifier
- `fk_session_id`: Reference to network session
- `timestamp`: Flow start time
- `duration_ms`: Flow duration
- `src_ip`, `dst_ip`, `src_port`, `dst_port`
- `protocol`: TCP, UDP, ICMP
- `packets`: Packet count
- `bytes`: Total bytes
- `tcp_flags`: TCP flag summary
- `router_id`: Exporting router
- `input_interface`, `output_interface`
- `tos`: Type of service

**Correlation:** Every network session generates netflow records

**Cardinality:** Derived from sessions (~12,000 flows)

### 11. IAM/Authentication Log Entity
Identity and access management events.

**Columns:**
- `auth_event_id`: Unique event identifier
- `fk_user_id`: Authenticating user
- `fk_host_id`: Source host (for workstation logins)
- `timestamp`: Event time
- `event_type`: login_success, login_failure, logout, password_change, privilege_escalation, account_lockout
- `auth_method`: password, mfa, certificate, sso, kerberos
- `target_system`: Workstation, VPN, Email, Application
- `source_ip`: Source IP address
- `failure_reason`: (for failures) invalid_password, account_disabled, mfa_timeout
- `is_anomalous`: Flag for unusual login patterns

**Cardinality:** ~5,000 auth events

## Correlation Strategy

### Primary Correlation: Network Session as Bridge

The `network_session` entity serves as the central correlation point:

1. **Host → Session**: Every network session is initiated by a host
2. **Session → Firewall**: All sessions pass through the firewall and generate logs
3. **Session → IDS**: Suspicious sessions trigger IDS alerts
4. **Session → DNS**: Sessions requiring name resolution generate DNS logs
5. **Session → Proxy**: HTTP/HTTPS sessions generate proxy logs
6. **Session → Netflow**: All sessions create netflow records

### Secondary Correlations

1. **User → Host**: Users are assigned to hosts
2. **User → VPN**: Remote users connect via VPN
3. **User → Auth**: All users have authentication events
4. **Host → Endpoint**: All hosts generate endpoint events

### Temporal Correlation

Events are correlated temporally:
- DNS query occurs BEFORE connection establishment
- Firewall log timestamp matches session initiation
- IDS alerts occur DURING established sessions
- Proxy logs correlate with HTTP session data transfer
- Netflow summarizes complete session duration

## Implementation Notes

### IP Address Scheme
- **Internal hosts**: 10.1.x.x (Segment A), 10.2.x.x (Segment B), 10.3.x.x (Segment C)
- **Servers/DMZ**: 172.16.x.x
- **VPN assigned**: 10.100.x.x
- **External destinations**: Public IP ranges (8.x.x.x, 104.x.x.x, etc.)

### Realistic Distributions
- **Traffic**: 80% internal, 20% external
- **Protocols**: 60% HTTPS, 20% HTTP, 10% DNS, 5% SSH/RDP, 5% other
- **IDS alerts**: 5-10% of sessions trigger alerts (mostly low severity)
- **Firewall blocks**: 2-5% of sessions blocked
- **Auth failures**: 5-10% of auth attempts fail

### Attack Scenarios (Optional)
The schema can support realistic attack patterns:
1. **Brute force**: Multiple auth failures from same source
2. **Lateral movement**: Internal-to-internal unusual connections
3. **Data exfiltration**: Large outbound transfers
4. **C2 communication**: Periodic beaconing patterns
5. **Privilege escalation**: Unusual process execution chains

- [ ] VPN logs correlate with remote host activity
